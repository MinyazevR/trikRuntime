# trikRos2 — интеграция ROS 2 с контроллером ТРИК

`trikRos2` — это модуль (динамическая библиотека `libtrikRos2.so`), который поднимает
узел (node) ROS 2 внутри процесса trikGui контроллера ТРИК. Узел даёт хосту (компьютеру
оператора, другому роботу и т.п.) доступ к датчикам, энкодерам, IMU (акселерометр и
гироскоп) контроллера через ROS 2 топики, а также позволяет управлять моторами и
сервоприводами, публикуя команды в соответствующие топики.

Модуль не создаёт отдельного экземпляра "железа" — он получает уже готовый
`BrickInterface`, с которым работает `trikGui`, поэтому с оборудованием одновременно
работает только один процесс, конфликтов доступа к портам нет.

## Совместимость

Узел собран под **ROS 2 Humble Hawksbill** и использует RMW-реализацию
**`rmw_cyclonedds_cpp`** (CycloneDDS). Чтобы хост и контроллер могли обнаружить друг
друга и обмениваться сообщениями, на хосте (и на любом другом устройстве, которое должно
взаимодействовать с контроллером ТРИК по ROS 2) нужно:

- использовать **ROS 2 Humble** (другие версии ROS 2 несовместимы по ABI сообщений
  и, как правило, по DDS wire-protocol в граничных случаях — не гарантируется);
- использовать **тот же RMW**, т.е. переменную окружения
  `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`. Если на хосте стоит RMW по умолчанию
  (`rmw_fastrtps_cpp`), узлы, скорее всего, друг друга не увидят;
- использовать общий `ROS_DOMAIN_ID` (по умолчанию `0` на обеих сторонах, если явно
  не менялся).

Стандартные типы сообщений, которые использует модуль — `std_msgs`, `sensor_msgs`,
`geometry_msgs` — из базовой поставки ROS2.

## Быстрый старт

1. Убедитесь, что в `/home/root/trik/ros2_config.xml` на контроллере настроены нужные
   порты (см. [ниже](#файл-конфигурации-ros2_configxml)). Если файла нет — узел
   запустится со всеми портами по умолчанию.
2. На контроллере: меню файлов → запустить `libtrikRos2.so.1`. Пока запуск активен —
   ROS 2 узел `trik` работает и виден в сети.
3. На хосте: `ros_domain_id` и `rmw_implementation` должны совпадать с контроллером
   (см. [Сетевое взаимодействие](#сетевое-взаимодействие-хост--контроллер)).
4. Проверить, что узел виден:
   ```bash
   ros2 node list          # должен появиться узел /trik
   ros2 topic list         # список топиков сенсоров/моторов/IMU
   ros2 topic echo /sensors/a1
   ```
5. Написать свой ROS 2 узел на хосте, который подписывается на нужные топики датчиков
   и публикует команды в топики моторов/сервоприводов (см.
   [примеры](#примеры-кода-на-хосте)).

## Запуск и остановка узла на контроллере

Модуль оформлен как обычная C++-программа ТРИК (`TrikCppProgram`), поэтому запускается
и останавливается так же, как любой скомпилированный `.so`-модуль:

- **Запуск** — в меню файлов на контроллере выбрать `libtrikRos2.so.1` и запустить.
  При старте модуль:
  - читает конфигурацию из `/home/root/trik/ros2_config.xml` (или использует настройки
    по умолчанию, если файла нет/он повреждён);
  - инициализирует `rclcpp` (если ещё не инициализирован) и создаёт узел с именем
    `trik`;
  - поднимает издателей и подписчиков согласно конфигурации;
  - запускает таймер публикации данных с частотой `rate_hz` из конфигурации;
  - крутит `SingleThreadedExecutor` в отдельном потоке.
- **Остановка** — обычная остановка запущенной программы на контроллере (кнопка
  "Стоп"/возврат к списку программ, как для любого другого запущенного модуля).
  При остановке узел корректно завершает поток `executor.spin()`, уничтожает объект
  узла и вызывает `rclcpp::shutdown()`.

Пока модуль не запущен — узла ROS 2 не существует, и никакие топики недоступны.

## Файл конфигурации ros2_config.xml

Путь на контроллере: **`/home/root/trik/ros2_config.xml`**.

Файл читается один раз, **при старте** модуля. Если после изменения конфигурации узел
уже запущен — его нужно **остановить и запустить заново** (через меню файлов), чтобы
изменения применились.

Если файл отсутствует, не открывается или содержит некорректный XML (неправильный
корневой элемент и т.п.) — используется встроенная конфигурация по умолчанию:
**все порты включены**, `rate_hz = 20.0` (см. также
[таблицу](#таблица-портов-по-умолчанию)).

### Структура файла

```xml
<?xml version="1.0" encoding="UTF-8"?>
<ros2config>

  <!-- rate_hz — частота публикации данных -->
  <params rate_hz="20.0"/>

  <!-- Датчики: публикуют sensor_msgs/Range на хост -->
  <sensors>
    <sensor port="A1" topic="sensors/a1"/>
    <sensor port="A2" topic="sensors/a2"/>
    <sensor port="A3" topic="sensors/a3"/>
    <sensor port="A4" topic="sensors/a4"/>
    <sensor port="A5" topic="sensors/a5"/>
    <sensor port="A6" topic="sensors/a6"/>
    <sensor port="D1" topic="sensors/d1"/>
    <sensor port="D2" topic="sensors/d2"/>
    <sensor port="D3" topic="sensors/d3"/>
  </sensors>

  <!-- Энкодеры: публикуют sensor_msgs/Range (значение в градусах) на хост -->
  <encoders>
    <encoder port="E1" topic="encoders/e1"/>
    <encoder port="E2" topic="encoders/e2"/>
    <encoder port="E3" topic="encoders/e3"/>
    <encoder port="E4" topic="encoders/e4"/>
  </encoders>

  <!-- Моторы: подписываются на std_msgs/Int32 с хоста -->
  <motors>
    <motor port="M1" topic="motors/m1"/>
    <motor port="M2" topic="motors/m2"/>
    <motor port="M3" topic="motors/m3"/>
    <motor port="M4" topic="motors/m4"/>
  </motors>

  <!-- Сервоприводы: подписываются на std_msgs/Int32 с хоста -->
  <servos>
    <servo port="S1" topic="servos/s1"/>
    <servo port="S2" topic="servos/s2"/>
    <servo port="S3" topic="servos/s3"/>
    <servo port="S4" topic="servos/s4"/>
    <servo port="S5" topic="servos/s5"/>
    <servo port="S6" topic="servos/s6"/>
  </servos>

  <!-- IMU: публикуют geometry_msgs/Vector3Stamped на хост. -->
  <imu>
    <accelerometer topic="imu/accelerometer"/>
    <gyroscope     topic="imu/gyroscope"/>
  </imu>

</ros2config>
```

### Параметр `rate_hz` — что это в терминах ROS 2

`rate_hz` — это частота внутреннего `wall timer`'а узла (`rclcpp::create_wall_timer`),
который **раз в `1/rate_hz` секунд опрашивает все датчики, энкодеры, акселерометр и
гироскоп и публикует по одному сообщению в каждый их топик**. То есть это **частота
публикации (publish rate) для всех издателей (publishers) сразу** — она общая на весь
узел, отдельно для каждого порта её задать нельзя.

**Важно:** `rate_hz` не влияет на моторы и сервоприводы. Подписчики команд
(`motors/*`, `servos/*`) реагируют на каждое входящее сообщение немедленно, по
событию (event-driven), а не по таймеру — см.
[раздел про подписчики](#подписчики-команды-хост--контроллер).

### Как отключить датчик/порт, который не нужен

Если какой-то порт (датчик, энкодер, мотор, сервопривод, акселерометр, гироскоп) не
используется в текущей задаче — закомментируйте соответствующую строку XML-комментарием
`<!-- ... -->`, например:

```xml
<sensors>
  <sensor port="A1" topic="sensors/a1"/>
  <!-- <sensor port="A2" topic="sensors/a2"/> -->
  <sensor port="A3" topic="sensors/a3"/>
  ...
</sensors>
```

Также можно просто удалить строку — результат тот же. После правки файла узел нужно
**перезапустить** (остановить `libtrikRos2.so.1` и запустить заново), чтобы изменения
конфигурации подхватились.

Так же можно переименовать `topic` для порта — например, если на хосте уже используются
другие имена топиков — просто измените атрибут `topic="..."` у нужного элемента.

## Топики: публикаторы и подписчики

### Публикаторы — данные идут с контроллера на хост

Публикуются раз в `1/rate_hz` секунд, для каждого настроенного порта — отдельный топик.

| Источник данных | Топик по умолчанию | Тип сообщения | Что в топике |
|---|---|---|---|
| Аналоговый датчик A1-A6 | `sensors/aN` | `sensor_msgs/msg/Range` | расстояние/показание датчика |
| Цифровой датчик D1-D3 | `sensors/dN` | `sensor_msgs/msg/Range` | показание датчика |
| Энкодер E1-E4 | `encoders/eN` | `sensor_msgs/msg/Range` | угол вала в градусах (упакован в поле `range`) |
| Акселерометр | `imu/accelerometer` | `geometry_msgs/msg/Vector3Stamped` | показания X/Y/Z |
| Гироскоп | `imu/gyroscope` | `geometry_msgs/msg/Vector3Stamped` | показания X/Y/Z |

### Подписчики — команды идут с хоста на контроллер

Реагируют на каждое полученное сообщение немедленно (событийно), очередь глубиной 1 —
имеет значение только последняя полученная команда.

| Приёмник команды | Топик по умолчанию | Тип сообщения | Что нужно прислать |
|---|---|---|---|
| Мотор M1-M4 | `motors/mN` | `std_msgs/msg/Int32` | мощность, целое число |
| Сервопривод S1-S6 | `servos/sN` | `std_msgs/msg/Int32` | мощность/угол, целое число |

## Форматы сообщений

### `sensor_msgs/msg/Range` — датчики A1-A6, D1-D3

```
std_msgs/Header header
  builtin_interfaces/Time stamp   # время публикации на контроллере
  string frame_id                # не заполняется, всегда "" (пустая строка)
uint8 radiation_type              # всегда INFRARED (85) — см. примечание ниже
float32 field_of_view             # 0.1 рад, фиксированное значение
float32 min_range                 # минимальное показание датчика, метры
float32 max_range                 # максимальное показание датчика, метры
float32 range                     # текущее показание датчика, метры
```

Как считаются `range`, `min_range`, `max_range`:

- контроллер читает сырое целочисленное значение датчика (`SensorInterface::read()`,
  единицы — сантиметры для дальномеров) и переводит в метры делением на 100:
  `range = read() * 0.01`;
- `min_range`/`max_range` берутся из `minValue()`/`maxValue()` датчика (границы,
  заданные в конфигурации модели робота) и так же переводятся в метры.

**Примечание:** поле `radiation_type` всегда равно `INFRARED`, а `field_of_view`
всегда `0.1` рад — это фиксированные значения, не зависящие от реального типа датчика
(на A5/A6, например, часто стоят датчики освещённости, а не дальномеры). Сообщение
`sensor_msgs/Range` переиспользуется как удобный стандартный контейнер "число + время +
диапазон", читайте в первую очередь поле `range` и, если нужно, `min_range`/`max_range`
для определения диапазона показаний конкретного порта. Если нужно сырое (не переведённое
в метры) значение — умножьте `range` на 100.

### `sensor_msgs/msg/Range` — энкодеры E1-E4

Тот же тип сообщения переиспользуется для энкодеров, но семантика полей другая:

```
std_msgs/Header header
  builtin_interfaces/Time stamp
  string frame_id                # не заполняется, всегда ""
uint8 radiation_type              # всегда INFRARED, значения не несёт
float32 field_of_view             # всегда 0.0, значения не несёт
float32 min_range                 # всегда 0.0, значения не несёт
float32 max_range                 # всегда 0.0, значения не несёт
float32 range                     # угол вала энкодера, ГРАДУСЫ (не метры!)
```

`range` — это `EncoderInterface::read()` (угол в градусах), приведённый к `float`, без
какого-либо масштабирования. Это накопительный счётчик тиков мотора, переведённый в
градусы (см. `Encoder::read()` в `trikControl`) — он растёт/уменьшается неограниченно и
сбрасывается только явным вызовом `reset()`, поэтому у него нет физического
минимума/максимума. Поля `min_range`/`max_range` не несут информации (всегда `0.0`) —
читайте только `range`. На хосте нужно привести `range` обратно к `int`, если нужно
целое число градусов:

```python
degrees = int(round(msg.range))
```

### `geometry_msgs/msg/Vector3Stamped` — акселерометр и гироскоп

```
std_msgs/Header header
  builtin_interfaces/Time stamp   # время публикации на контроллере
  string frame_id                 # не заполняется, всегда ""
geometry_msgs/Vector3 vector
  float64 x
  float64 y
  float64 z
```

`x`, `y`, `z` — это **целочисленные показания** датчиков (значения из
`VectorSensorInterface::read()`, приведённые к `double`) акселерометра или гироскопа по осям X, Y, Z.

### `std_msgs/msg/Int32` — моторы и сервоприводы (команды)

```
int32 data
```

Хосту достаточно опубликовать одно сообщение с полем `data` —
контроллер немедленно вызовет `setPower(data)` на соответствующем моторе/сервоприводе.
Значения вне диапазона будут ограничены (constrained) самим драйвером мотора.

## Сетевое взаимодействие хост ⇄ контроллер

Так как используется CycloneDDS, для обнаружения узлов друг другом нужно:

1. **Одинаковый `ROS_DOMAIN_ID`** на хосте и контроллере (по умолчанию `0` с обеих
   сторон, если не менялся явно):
   ```bash
   export ROS_DOMAIN_ID=0
   ```
2. **Одинаковый RMW** — на хосте обязательно выставить:
   ```bash
   export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
   ```
3. **Работающий multicast/discovery** между хостом и контроллером. Если оба устройства
   в одной Wi-Fi/Ethernet сети с работающим multicast (например, оба подключены к точке
   доступа робота) — обнаружение обычно происходит автоматически.

   Если multicast не работает (разные подсети, Docker-контейнер на хосте без
   `--network host`, некоторые Wi-Fi роутеры блокируют multicast между клиентами) —
   нужно явно указать CycloneDDS адрес контроллера через конфигурационный файл на
   стороне хоста:

   ```xml
   <!-- cyclonedds.xml на хосте -->
   <CycloneDDS>
     <Domain>
       <Discovery>
         <Peers>
           <!-- IP контроллера ТРИК в локальной сети -->
           <Peer address="192.168.1.100"/>
         </Peers>
       </Discovery>
     </Domain>
   </CycloneDDS>
   ```

   и передать путь к нему через переменную окружения перед запуском узла хоста:
   ```bash
   export CYCLONEDDS_URI="file:///path/to/cyclonedds.xml"
   ```

   IP-адрес контроллера можно узнать на самом контроллере в главном меню интерфейса.

4. Если хост запускается в Docker — контейнер должен использовать `--network host`
   (или явно пробрасывать UDP-порты DDS), иначе multicast/DDS-трафик не дойдёт до
   контроллера.

## Примеры кода на хосте

Документация описывает только сторону контроллера — код на хосте пишет пользователь
самостоятельно на любом языке, поддерживаемом ROS 2 (C++, Python и т.д.). Ниже —
минимальные иллюстративные примеры того, как подписаться на датчик и как отправить
команду мотору, чтобы показать использование описанных выше топиков и типов сообщений.

### Проверка топиков без написания кода

```bash
# что публикует контроллер прямо сейчас
ros2 topic echo /sensors/a1
ros2 topic echo /encoders/e1
ros2 topic echo /imu/accelerometer

# отправить мотору M1 команду "мощность 50"
ros2 topic pub --once /motors/m1 std_msgs/msg/Int32 "{data: 50}"

# остановить мотор
ros2 topic pub --once /motors/m1 std_msgs/msg/Int32 "{data: 0}"
```

### C++ (rclcpp)

```cpp
#include <rclcpp/rclcpp.hpp>
#include <sensor_msgs/msg/range.hpp>
#include <std_msgs/msg/int32.hpp>

class TrikExample : public rclcpp::Node {
public:
    TrikExample() : Node("trik_example") {
        motor_m1_ = create_publisher<std_msgs::msg::Int32>("motors/m1", 1);

        sensor_a1_ = create_subscription<sensor_msgs::msg::Range>(
            "sensors/a1", 10,
            [this](sensor_msgs::msg::Range::SharedPtr msg) {
                RCLCPP_INFO(get_logger(), "A1 = %.3f m", msg->range);

                std_msgs::msg::Int32 cmd;
                cmd.data = (msg->range < 0.10) ? 0 : 40;
                motor_m1_->publish(cmd);
            });
    }

private:
    rclcpp::Subscription<sensor_msgs::msg::Range>::SharedPtr sensor_a1_;
    rclcpp::Publisher<std_msgs::msg::Int32>::SharedPtr motor_m1_;
};

int main(int argc, char ** argv) {
    rclcpp::init(argc, argv);
    rclcpp::spin(std::make_shared<TrikExample>());
    rclcpp::shutdown();
    return 0;
}
```
